Part 1: The Program Development Life Cycle & Decomposition

1. The Program Development Life Cycle (PDLC)

The PDLC consists of four main stages required to develop a software solution:

  • Analysis:  Identifying the problem and requirements. This stage involves:
  • Abstraction:  Keeping the key elements required for the solution and discarding any unnecessary details.
  • Decomposition:  Breaking down a complex problem into its smaller, more manageable component parts.
  • Design:  Planning the solution. This involves using decomposition, structure diagrams , flowcharts , and pseudocode .
  • Coding:  Writing the actual program code using a programming language, accompanied by iterative testing  (testing and amending code repeatedly during development).
  • Testing:  Running the completed program with various sets of test data to ensure all tasks work together as specified.

2. Computer Systems and Decomposition

  1. Every computer system is made up of sub-systems , which can be further divided into even smaller sub-systems until each performs a single action (known as Top-down design  and stepwise refinement ).
  2. When decomposing a problem, any computer system can be broken down into four component parts:
  3. Inputs:  The data entered into the system.
  4. Processes:  The tasks performed using the input data.
  5. Outputs:  The information displayed or printed for the user.
  6. Storage:  Data saved in files on an appropriate medium for future use.

Part 2: Methods of Designing and Constructing Solutions

1. Design Tools

  • Structure Diagrams:  Hierarchical diagrams showing how a computer system solution is divided into sub-systems, with each level giving a more detailed breakdown.
  • Flowcharts:  A diagrammatic representation showing the steps required to complete a task and their order. Standard symbols include:
  • Terminator (Oval):  Start/Stop.
  • Input/Output (Parallelogram):  Entering data or displaying results.
  • Process (Rectangle):  An action or calculation (e.g., assigning variables).
  • Decision (Diamond):  A Yes/No or True/False question that splits the flow.
  • Pseudocode:  A text-based method of designing algorithms using English keywords (e.g., INPUT, OUTPUT, IF, WHILE) that pretend to be programming code with precise statements and a consistent notation.

2. Explaining and Amending Algorithms

  • You must be able to state the purpose of a given algorithm and describe the processes involved.
  • Algorithms need to include variables, outputs, and user prompts  (e.g., OUTPUT "Please enter your name").

Part 3: Standard Methods of Solution

Algorithms frequently use standard methods that can be applied to many different problems:

  • Totalling:  Keeping a running total by adding values together (e.g., Total ← Total + Mark).
  • Counting:  Keeping track of the number of times an action is performed (e.g., Count ← Count + 1 or counting down items in stock).
  • Finding Maximum, Minimum, and Average:
  • Max/Min:  Looping through a list and continuously replacing the highest/lowest stored value if a new higher/lower value is found.
  • Average:  Calculated by dividing the Total by the Count.
  • Linear Search:  Systematically working through items in a list, one by one, to check if an item matches the value being searched for.
  • Bubble Sort:  Sorting a list into ascending or descending order. It works by comparing each element with the next element and swapping them if they are in the wrong order. This process passes through the list repeatedly until no more swaps are made.

Part 4: Validation and Verification

Input checks help reject unreasonable data and detect copying errors. Validation alone cannot prove that data is accurate.

1. Validation (Automated Checks)

Validation is the automated checking by a program to ensure data is reasonable and allowable before it is accepted. If rejected, an error message is output.

  • Range check:  Checks that a number is between a specific upper and lower boundary (e.g., a test mark must be between 0 and 100).
  • Length check:  Checks that data contains an exact number of characters (e.g., a password must be exactly 8 characters) or fits within a reasonable length.
  • Type check:  Checks that the data entered is of the correct data type (e.g., ensuring an integer is entered, not text).
  • Presence check:  Checks that data has actually been entered and not left blank (e.g., an email address is required).
  • Format check:  Checks that the characters conform to a pre-defined pattern (e.g., a student ID must be 3 letters followed by 4 numbers).
  • Check digit:  A final digit appended to a code (like an ISBN or barcode) calculated from the other digits. It can detect some data entry errors; which errors it detects depends on the check-digit algorithm.

2. Verification (Human/Copying Checks)

Verification checks that data has been accurately copied from one source to another without changing.

  • Double entry check:  The data is entered twice (sometimes by two different operators). The computer compares both entries and rejects them if they do not match perfectly.
  • Visual/Screen check:  The user manually reads and checks the data displayed on the screen against the original paper document before confirming it is correct.

Part 5: Testing and Trace Tables

1. Types of Test Data

To prove an algorithm or program works correctly, it must be tested using specific sets of data:

  • Normal data:  Typical data that the program should normally accept (e.g., if the range is 0-100, entering 50).
  • Abnormal (Erroneous) data:  Data that should be rejected by the solution (e.g., entering "ten" or -15).
  • Extreme data:  The largest and smallest acceptable values within normal data (e.g., exactly 0 and exactly 100).
  • Boundary data:  Two values used at each edge of a limit—one is the largest/smallest acceptable value, and the other is the corresponding smallest/largest rejected value (e.g., testing the boundary 100 by entering 100 (accepted) and 101 (rejected)).

2. Trace Tables and Dry Runs

  • Dry Run:  The manual exercise of working through an algorithm step-by-step to see what it does.
  • Trace Table:  Used to document a dry run. It has columns for every variable, condition, and output. Every time a variable's value changes in the algorithm, the new value is recorded in a new row of the table.

3. Identifying and Correcting Errors

  • By performing a dry run with test data and logging it in a trace table, logical errors in an algorithm become visible (e.g., an algorithm failing to find the smallest number because the initial minimum variable was set too low).
  • Once errors are identified, algorithms must be amended and re-tested using pseudocode, flowcharts, or program code until the solution works perfectly.
